Задача, которую сформулировала княгиня, – это задача настройки доступа к удалённому хранилищу. Она состоит из двух частей, и они решаются разными средствами.

**Первая часть: по каким правилам живёт сервер.** Какие у него настройки, где они записаны, какие можно изменить немедленно, а какие только остановив работу.

**Вторая часть: кого он слушает.** С каких адресов, от имени каких ролей и к каким базам данных разрешено подключаться, и как это проверить, не дожидаясь отказа.

::: info Что мы изучаем в этом учебном вопросе
**Параметры конфигурации**: где они хранятся, как узнать текущее значение и его источник, как изменить на уровне сеанса, роли, базы данных и всего сервера, и в каком порядке эти уровни перебивают друг друга.

**Применение изменений**: какие параметры действуют сразу, какие после перезагрузки конфигурации, а какие требуют перезапуска сервера.

**Файлы конфигурации**: `postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf`, и средства проверки того, что сервер их действительно прочитал.

**Удалённое подключение**: параметр `listen_addresses`, правила `pg_hba.conf`, методы проверки подлинности и настройка клиентской стороны.
:::

## Рабочая среда

Как и в предыдущих занятиях, работаем на учебном сервере. Но у этого учебного вопроса есть особенность:

::: warning Часть заданий требует доступа к файловой системе сервера
Файлы `postgresql.conf` и `pg_hba.conf` правятся текстовым редактором **на той машине, где работает сервер**. Ни pgAdmin, ни DBeaver этого не умеют: они работают с базой данных, а не с файлами.

Поэтому для выполнения заданий второй половины нужен доступ к серверу – по SSH в Linux или через удалённый рабочий стол в Windows – и права пользователя операционной системы, от имени которого запущен сервер.

Перезапуск сервера также выполняется средствами операционной системы, а не SQL-командой.

Если доступа к файловой системе нет, задания первой половины (просмотр и изменение параметров через SQL) выполнимы полностью, а задания второй половины следует разобрать по описанию.
:::

Задания раздела про удалённое подключение выполняются **в парах**: один обучающийся настраивает сервер, второй подключается к нему как клиент, затем они меняются ролями.

## Где живут настройки сервера

### Три источника значения

Значение любого параметра берётся из одного из трёх мест, и сервер всегда знает, из какого именно.

**Встроенное значение по умолчанию.** Задано в исходном коде и применяется, если параметр не упомянут нигде.

**Файлы конфигурации.** Читаются при запуске сервера и при перезагрузке конфигурации.

**Установка во время работы.** Параметры, заданные для текущего сеанса, транзакции, роли или базы данных.

### Главный каталог: pg_settings

Все параметры сервера представлены в системном представлении `pg_settings` – по одной строке на параметр. Это основной инструмент работы с конфигурацией, и его столбцы стоит разобрать подробно.

```sql
SELECT count(*) AS всего_параметров FROM pg_settings;
```

В современных версиях число приближается к четырёмстам.

Посмотрим на один параметр во всех подробностях. В `psql` предварительно включите расширенный режим командой `\x`:

```sql
SELECT name, setting, unit, boot_val, reset_val,
       source, sourcefile, sourceline,
       context, vartype, min_val, max_val,
       pending_restart, short_desc
FROM pg_settings
WHERE name = 'work_mem';
```

Назначение столбцов:

| Столбец | Содержание |
| :--- | :--- |
| `name` | Имя параметра |
| `setting` | **Текущее** действующее значение в текущем сеансе |
| `unit` | Единица измерения: `kB`, `8kB`, `ms`, `s`, `min` |
| `boot_val` | Встроенное значение по умолчанию |
| `reset_val` | Значение, к которому вернёт команда `RESET` |
| `source` | Откуда взято текущее значение |
| `sourcefile` | Путь к файлу, если значение из файла |
| `sourceline` | Номер строки в этом файле |
| `context` | Когда изменение может быть применено |
| `vartype` | Тип: `bool`, `integer`, `real`, `string`, `enum` |
| `min_val`, `max_val` | Допустимые границы для числовых параметров |
| `enumvals` | Список допустимых значений для перечисляемых |
| `pending_restart` | Значение изменено в файле, но требует перезапуска |
| `short_desc`, `extra_desc` | Описание на английском языке |

::: tip Единицы измерения и столбец unit
Это место, где легко ошибиться. Значение в столбце `setting` выражено **в единицах столбца `unit`**, а не в тех, в которых вы его задавали.

Если задать `work_mem = '16MB'`, то в `setting` окажется `16384`, а в `unit` – `kB`. Параметр `shared_buffers` вообще измеряется в блоках по 8 КБ: значение `16384` означает 128 МБ.

Поэтому для чтения значений в привычном виде пользуются функцией `current_setting`, которая возвращает их так, как они были заданы:

```sql
SELECT current_setting('work_mem')      AS work_mem,
       current_setting('shared_buffers') AS shared_buffers;
```

Либо командой `SHOW`, которая делает то же самое.
:::

### Источник значения

Столбец `source` показывает, откуда сервер взял текущее значение. Возможные значения перечислены в порядке возрастания приоритета:

| Значение `source` | Что означает |
| :--- | :--- |
| `default` | Встроенное значение по умолчанию |
| `configuration file` | Из `postgresql.conf` или `postgresql.auto.conf` |
| `command line` | Из параметров запуска сервера |
| `environment variable` | Из переменной окружения |
| `database` | Задано командой `ALTER DATABASE` |
| `user` | Задано командой `ALTER ROLE` |
| `client` | Передано клиентом при подключении |
| `session` | Задано командой `SET` в текущем сеансе |
| `override` | Переопределено внутренней логикой сервера |

Посмотреть распределение всех параметров по источникам:

```sql
SELECT source AS источник, count(*) AS параметров
FROM pg_settings
GROUP BY source
ORDER BY count(*) DESC;
```

На свежеустановленном сервере подавляющее большинство параметров имеет источник `default`, и это нормально: настройки по умолчанию рассчитаны на работоспособность в любых условиях.

Найти все параметры, отличающиеся от значений по умолчанию, – первое, что делают при разборе незнакомого сервера:

```sql
SELECT name       AS параметр,
       setting    AS значение,
       boot_val   AS по_умолчанию,
       source     AS источник,
       sourcefile AS файл,
       sourceline AS строка
FROM pg_settings
WHERE source NOT IN ('default', 'override')
ORDER BY source, name;
```

## Классы применимости изменений

### Столбец context

Это самый важный для администратора столбец `pg_settings`. Он отвечает на вопрос: **что нужно сделать, чтобы изменение подействовало.**

```sql
SELECT context AS класс, count(*) AS параметров
FROM pg_settings
GROUP BY context
ORDER BY count(*) DESC;
```

Классов семь:

| Класс | Кто и когда может изменить |
| :--- | :--- |
| `internal` | **Никто.** Значение определено при сборке или инициализации кластера |
| `postmaster` | Только правкой файла и **перезапуском сервера** |
| `sighup` | Правкой файла и **перезагрузкой конфигурации**, без перезапуска |
| `superuser-backend` | Как `sighup`, а также клиентом при установлении соединения, если он суперпользователь |
| `backend` | Как `sighup`, а также клиентом при установлении соединения |
| `superuser` | Командой `SET` в сеансе, но только суперпользователем или ролью с соответствующим правом |
| `user` | Командой `SET` в сеансе любой ролью |

::: info Почему это разделение существует
Оно отражает техническое устройство сервера.

PostgreSQL работает как **множество процессов**: один главный процесс и по одному обслуживающему процессу на каждое соединение, плюс фоновые процессы.

Параметры класса `postmaster` определяют то, что создаётся **один раз при запуске главного процесса**: размер разделяемой памяти, число слотов под соединения, прослушиваемые адреса. Изменить их на ходу невозможно, потому что структуры уже созданы и на них рассчитаны все остальные процессы.

Параметры класса `sighup` читаются процессами **повторно**, когда главный процесс рассылает им сигнал. Поэтому их можно менять без остановки.

Параметры класса `user` существуют у каждого обслуживающего процесса **независимо**: размер памяти под сортировку, время ожидания, путь поиска. Один сеанс может работать с одними значениями, другой – с другими.
:::

Примеры параметров каждого класса:

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN ('block_size', 'max_connections', 'shared_buffers',
               'listen_addresses', 'port', 'log_min_duration_statement',
               'autovacuum_naptime', 'work_mem', 'statement_timeout',
               'search_path')
ORDER BY context, name;
```

| Параметр | Класс | Почему |
| :--- | :--- | :--- |
| `block_size` | `internal` | Размер страницы задан при сборке, изменению не подлежит |
| `max_connections` | `postmaster` | Под соединения выделяются структуры в разделяемой памяти |
| `shared_buffers` | `postmaster` | Буферный кэш создаётся при запуске |
| `listen_addresses` | `postmaster` | Сокеты открываются при запуске |
| `port` | `postmaster` | То же |
| `log_min_duration_statement` | `sighup` | Касается только протоколирования |
| `autovacuum_naptime` | `sighup` | Фоновый процесс перечитывает значение |
| `work_mem` | `user` | У каждого сеанса своё |
| `statement_timeout` | `user` | У каждого сеанса своё |
| `search_path` | `user` | У каждого сеанса свой |

::: tip Практический вывод
Прежде чем менять параметр, посмотрите его класс:

```sql
SELECT name, context FROM pg_settings WHERE name = 'shared_buffers';
```

Если класс `postmaster`, планируйте окно технического обслуживания: без перезапуска изменение не подействует, и никакая перезагрузка конфигурации не поможет.

Это уберегает от ситуации, когда администратор правит файл, перезагружает конфигурацию, не видит изменений и начинает искать несуществующую ошибку.
:::

## Изменение параметров

### Уровень сеанса и транзакции

Команда `SET` задаёт значение на время **текущего сеанса**:

```sql
SHOW work_mem;

SET work_mem = '16MB';

SHOW work_mem;
```

Команда `RESET` возвращает значение, действовавшее до этого, то есть `reset_val`:

```sql
RESET work_mem;

SHOW work_mem;
```

Форма `SET LOCAL` задаёт значение на время **текущей транзакции**:

```sql
BEGIN;

SET LOCAL work_mem = '128MB';

SELECT current_setting('work_mem') AS внутри_транзакции;

COMMIT;

SELECT current_setting('work_mem') AS после_фиксации;
```

Внутри транзакции действует новое значение, после её завершения – прежнее. Это удобно для одного тяжёлого запроса: увеличить память под сортировку только для него, не затрагивая остальную работу сеанса.

::: info Функциональный эквивалент: set_config
Та же операция доступна в виде функции, что позволяет вычислять значение выражением:

```sql
SELECT set_config('work_mem', '32MB', false);

SHOW work_mem;

SELECT set_config('work_mem', '4MB', false);
```

Третий аргумент соответствует разнице между `SET` и `SET LOCAL`: значение `false` означает «на весь сеанс», `true` – «только на транзакцию».

Функция незаменима в двух случаях: когда имя или значение параметра приходит из данных, и когда установку надо выполнить внутри запроса, где команда `SET` недопустима.
:::

Сбросить все параметры сеанса сразу:

```sql
RESET ALL;
```

### Уровень роли и базы данных

Значение можно закрепить за ролью или за базой данных. Оно будет применяться при каждом подключении.

```sql
ALTER DATABASE postgres SET work_mem = '8MB';

ALTER ROLE CURRENT_USER SET statement_timeout = '30s';
```

Комбинация обоих уровней – значение действует только при подключении указанной роли к указанной базе:

```sql
ALTER ROLE CURRENT_USER IN DATABASE postgres SET work_mem = '64MB';
```

Посмотреть все установки этого уровня:

```sql
SELECT coalesce(d.datname, '<все базы>') AS база,
       coalesce(r.rolname, '<все роли>') AS роль,
       s.setconfig                       AS параметры
FROM pg_db_role_setting s
LEFT JOIN pg_database d ON d.oid = s.setdatabase
LEFT JOIN pg_roles    r ON r.oid = s.setrole;
```

Отмена:

```sql
ALTER DATABASE postgres RESET work_mem;

ALTER ROLE CURRENT_USER RESET statement_timeout;

ALTER ROLE CURRENT_USER IN DATABASE postgres RESET work_mem;
```

::: tip Для чего это применяют на практике
Три типовых случая.

**Ограничение приложения.** Роли, от имени которой работает веб-приложение, задают `statement_timeout`, чтобы ни один запрос не висел дольше разумного.

**Настройка отчётной роли.** Роли, выполняющей тяжёлую аналитику, задают увеличенный `work_mem` и снятый `statement_timeout`: её запросы заведомо долгие и требуют много памяти.

**Путь поиска.** Роли задают `search_path`, соответствующий её схеме, чтобы приложение не писало полные имена.

Все три настройки не затрагивают остальные сеансы, что и является их главным достоинством.
:::

### Уровень всего сервера: ALTER SYSTEM

Команда `ALTER SYSTEM` изменяет параметр для **всего сервера**, записывая его в файл `postgresql.auto.conf`:

```sql
ALTER SYSTEM SET log_min_duration_statement = '500ms';
```

::: warning ALTER SYSTEM нельзя выполнить внутри транзакции
Попытка завершится ошибкой:

```
ERROR:  ALTER SYSTEM cannot run inside a transaction block
```

Причина в том, что команда записывает файл на диске, а файловую операцию невозможно откатить вместе с транзакцией.

На практике это означает, что в графических клиентах, оборачивающих команды в транзакцию, `ALTER SYSTEM` может не работать. В DBeaver надо включить автофиксацию, в pgAdmin команда работает, поскольку Query Tool по умолчанию её не оборачивает.
:::

Сама команда значение **не применяет**: она только записывает его в файл. Чтобы оно подействовало, конфигурацию надо перезагрузить:

```sql
SELECT pg_reload_conf();
```

Проверим результат:

```sql
SELECT name, setting, source, sourcefile, pending_restart
FROM pg_settings
WHERE name = 'log_min_duration_statement';
```

Столбец `source` стал `configuration file`, а `sourcefile` указывает на `postgresql.auto.conf`.

Отмена:

```sql
ALTER SYSTEM RESET log_min_duration_statement;

SELECT pg_reload_conf();
```

Сбросить все установки, сделанные через `ALTER SYSTEM`:

```sql
ALTER SYSTEM RESET ALL;
```

### Файл postgresql.auto.conf

Этот файл лежит в каталоге данных и создаётся командой `ALTER SYSTEM`. Его содержимое выглядит так:

```
# Do not edit this file manually!
# It will be overwritten by the ALTER SYSTEM command.
log_min_duration_statement = '500ms'
```

::: danger Почему его не правят руками
Предупреждение в первых строках не формальность. Файл **перезаписывается целиком** при каждом выполнении `ALTER SYSTEM`, и ручные правки будут потеряны без предупреждения.

Кроме того, `postgresql.auto.conf` читается **после** `postgresql.conf`, и потому перебивает его. Это источник одной из самых запутанных ситуаций: администратор правит `postgresql.conf`, перезагружает конфигурацию, а значение не меняется, потому что тот же параметр установлен через `ALTER SYSTEM` и лежит в `auto.conf`.

Диагностируется это одним запросом – по столбцу `sourcefile`:

```sql
SELECT name, setting, sourcefile, sourceline
FROM pg_settings
WHERE name = 'work_mem';
```

Если в `sourcefile` стоит `postgresql.auto.conf`, правка основного файла бесполезна, пока установка не снята командой `ALTER SYSTEM RESET`.
:::

### Параметры, требующие перезапуска

Посмотрим, что произойдёт при изменении параметра класса `postmaster`:

```sql
ALTER SYSTEM SET max_connections = 200;
```

```sql
SELECT pg_reload_conf();
```

```sql
SELECT name, setting, pending_restart
FROM pg_settings
WHERE name = 'max_connections';
```

Значение в столбце `setting` **осталось прежним**, а столбец `pending_restart` получил значение `true`. Это сервер сообщает: новое значение прочитано из файла, но применить его без перезапуска невозможно.

Найти все такие параметры:

```sql
SELECT name, setting, pending_restart
FROM pg_settings
WHERE pending_restart;
```

Отменим изменение:

```sql
ALTER SYSTEM RESET max_connections;
```

```sql
SELECT pg_reload_conf();
```

::: tip Привычка, экономящая часы
После любой правки конфигурации выполняйте два запроса: один на `pending_restart`, второй – на интересующий параметр с проверкой `source` и `sourcefile`.

Первый скажет, нужен ли перезапуск. Второй – действительно ли подхвачено ваше значение и из какого файла.

Без этих двух проверок «настроил, но не работает» превращается в поиск вслепую.
:::

## Иерархия уровней установки

Сведём воедино. Один и тот же параметр может быть задан на семи уровнях, и они перебивают друг друга в строгом порядке. Ниже – от самого слабого к самому сильному:

| Уровень | Чем задаётся | Область действия |
| :--- | :--- | :--- |
| 1. Встроенное значение | Исходный код | Всё, если не задано иначе |
| 2. Файл `postgresql.conf` | Правка файла | Весь сервер |
| 3. Файл `postgresql.auto.conf` | `ALTER SYSTEM` | Весь сервер |
| 4. Командная строка запуска | Параметры `pg_ctl` или службы | Весь сервер |
| 5. База данных | `ALTER DATABASE ... SET` | Все подключения к базе |
| 6. Роль | `ALTER ROLE ... SET` | Все подключения роли |
| 7. Роль в базе | `ALTER ROLE ... IN DATABASE ... SET` | Подключения роли к этой базе |
| 8. Сеанс | `SET` | Текущий сеанс |
| 9. Транзакция | `SET LOCAL` | Текущая транзакция |

Чем ниже уровень в таблице, тем он сильнее. Значение, заданное командой `SET` в сеансе, перебьёт и файл, и установку роли.

::: warning Единственное исключение
Параметры класса `postmaster` могут быть заданы только на уровнях 2–4. Попытка задать их на уровне роли, базы или сеанса завершится ошибкой:

```
ERROR:  parameter "shared_buffers" cannot be changed without restarting the server
```

Это согласуется с разделением на классы: раз структуры создаются при запуске, никакой сеанс изменить их не может.
:::

Разобраться, какой уровень сработал, помогает всё тот же `source`:

```sql
SELECT name, setting, source, sourcefile, sourceline
FROM pg_settings
WHERE name = 'work_mem';
```

## Проверка файлов конфигурации

### Представление pg_file_settings

Представление `pg_settings` показывает **действующие** значения. Представление `pg_file_settings` показывает, что написано **в файлах**, включая строки, которые не подействовали.

```sql
SELECT sourcefile, sourceline, name, setting, applied, error
FROM pg_file_settings
ORDER BY sourcefile, sourceline;
```

Два последних столбца и составляют ценность этого представления:

| Столбец | Содержание |
| :--- | :--- |
| `applied` | Применена ли эта строка файла |
| `error` | Причина, по которой не применена |

::: tip Как находить ошибки в конфигурации
Строка файла может не примениться по двум причинам: она перебита более поздней строкой того же или другого файла, либо в ней ошибка.

Запрос, выводящий все проблемные строки:

```sql
SELECT sourcefile, sourceline, name, setting, error
FROM pg_file_settings
WHERE NOT applied;
```

Это единственный способ увидеть опечатку в имени параметра, не перезапуская сервер. При перезагрузке конфигурации сервер сообщает об ошибках в журнал, но не отказывается работать, и незамеченная опечатка может месяцами оставаться в файле.
:::

### Структура файла postgresql.conf

Файл лежит в каталоге данных. Узнать точный путь:

```sql
SHOW config_file;
```

Прочие пути:

```sql
SELECT name, setting
FROM pg_settings
WHERE name IN ('config_file', 'hba_file', 'ident_file', 'data_directory');
```

Формат файла прост: по одному параметру на строку, комментарии начинаются со знака решётки.

```
# -----------------------------
# Подключения
# -----------------------------
listen_addresses = '*'
port = 5432
max_connections = 100

# -----------------------------
# Память
# -----------------------------
shared_buffers = 2GB
work_mem = 16MB
maintenance_work_mem = 512MB
```

::: info Правило последнего вхождения
Если параметр упомянут в файле дважды, действует **последнее** вхождение. Предыдущие попадут в `pg_file_settings` со значением `applied = false`.

Это сделано намеренно и используется: файл можно разбить на части, подключив их директивами

```
include 'conf.d/memory.conf'
include_dir 'conf.d'
include_if_exists 'local.conf'
```

Подключённые файлы читаются в месте директивы, и параметры из них перебивают заданные выше. Такая организация удобна при управлении конфигурацией через средства автоматизации: общая часть лежит в основном файле, а машинно-зависимая – в подключаемом.
:::

### Перезагрузка конфигурации

Три равнозначных способа, различающихся лишь тем, откуда выполняются:

**Из базы данных:**

```sql
SELECT pg_reload_conf();
```

**Из командной строки средствами PostgreSQL:**

```bash
pg_ctl reload -D /var/lib/postgresql/16/main
```

**Средствами операционной системы:**

```bash
sudo systemctl reload postgresql
```

Все три приводят к тому, что главный процесс получает сигнал `SIGHUP` и рассылает его дочерним, после чего они перечитывают файлы конфигурации.

Перезапуск, нужный для параметров класса `postmaster`, выполняется только средствами операционной системы:

```bash
sudo systemctl restart postgresql
```

::: danger Различие перезагрузки и перезапуска
**Перезагрузка конфигурации** не разрывает соединений и не прерывает работу. Применяются параметры классов `sighup` и слабее.

**Перезапуск** останавливает сервер и запускает заново. Все соединения разрываются, незафиксированные транзакции откатываются, буферный кэш очищается и наполняется заново, из-за чего первые минуты после перезапуска производительность ниже обычной.

Поэтому перезапуск планируют, а перезагрузку выполняют свободно.
:::

## Основные параметры

Полное изучение всех параметров выходит за рамки курса. Перечислим те, которые администратор настраивает в первую очередь.

### Подключения

| Параметр | Класс | Назначение |
| :--- | :--- | :--- |
| `listen_addresses` | `postmaster` | С каких сетевых адресов сервер принимает подключения |
| `port` | `postmaster` | Номер порта |
| `max_connections` | `postmaster` | Предел одновременных подключений |
| `superuser_reserved_connections` | `postmaster` | Сколько соединений зарезервировано под суперпользователя |

::: tip Зачем резервировать соединения
Параметр `superuser_reserved_connections` решает важную задачу. Если приложение исчерпает все соединения, администратор не сможет подключиться, чтобы разобраться. Зарезервированные слоты гарантируют, что суперпользователь войдёт даже тогда, когда для всех остальных мест нет.
:::

### Память

| Параметр | Класс | Назначение |
| :--- | :--- | :--- |
| `shared_buffers` | `postmaster` | Размер общего буферного кэша страниц |
| `work_mem` | `user` | Память на одну операцию сортировки или хеширования |
| `maintenance_work_mem` | `user` | Память для обслуживающих операций: очистки, построения индексов |
| `effective_cache_size` | `user` | Подсказка планировщику об объёме кэша операционной системы |

::: warning Коварство параметра work_mem
Это значение выделяется **не на сеанс, а на операцию**. Запрос с тремя сортировками и двумя хеш-соединениями может затребовать пятикратный `work_mem`. Умножьте на число одновременных соединений – и получите величину, способную исчерпать всю память сервера.

Поэтому `work_mem` устанавливают умеренным глобально и повышают точечно, на уровне отчётной роли или отдельного сеанса, как разобрано выше.

Признак нехватки `work_mem` виден в планах запросов: узлы `Sort` и `Hash` получают пометку о работе через диск. Это разбиралось в учебном вопросе об индексах.
:::

### Журнал предзаписи

| Параметр | Класс | Назначение |
| :--- | :--- | :--- |
| `wal_level` | `postmaster` | Объём сведений, записываемых в журнал |
| `max_wal_size`, `min_wal_size` | `sighup` | Границы размера журнала между контрольными точками |
| `checkpoint_timeout` | `sighup` | Максимальный интервал между контрольными точками |
| `archive_mode`, `archive_command` | `postmaster`, `sighup` | Архивирование журнала для восстановления на момент времени |

Параметр `wal_level` принимает три значения: `minimal` – только для восстановления после сбоя, `replica` – достаточно для репликации и резервных копий, `logical` – достаточно для логической репликации. Значение по умолчанию `replica`; к этому параметру мы вернёмся в учебном вопросе о резервном копировании.

### Протоколирование

| Параметр | Класс | Назначение |
| :--- | :--- | :--- |
| `logging_collector` | `postmaster` | Писать журнал в файлы, а не в стандартный вывод |
| `log_directory`, `log_filename` | `sighup` | Куда и под каким именем |
| `log_min_duration_statement` | `superuser` | Протоколировать запросы длительнее указанного времени |
| `log_statement` | `superuser` | Протоколировать команды: `none`, `ddl`, `mod`, `all` |
| `log_connections`, `log_disconnections` | `superuser` | Протоколировать подключения и отключения |
| `log_lock_waits` | `superuser` | Протоколировать длительные ожидания блокировок |
| `log_line_prefix` | `sighup` | Формат начала каждой строки журнала |

::: tip Минимальный разумный набор для журнала
На рабочем сервере стоит включить как минимум:

- `log_min_duration_statement` порядка одной секунды – чтобы видеть медленные запросы;
- `log_lock_waits` – чтобы видеть, кто кого блокировал;
- `log_connections` и `log_disconnections` – для разбора вопросов доступа;
- `log_line_prefix` с указанием времени, идентификатора процесса, имени роли и базы данных.

Значение `log_statement = 'all'` на нагруженном сервере включать не следует: журнал будет расти гигабайтами в сутки и сам станет источником проблем.
:::

## Удалённое подключение

Переходим ко второй части вопроса. Чтобы клиент с другой машины смог подключиться к серверу, должны выполниться **три условия**, и настраиваются они в разных местах.

| Условие | Где настраивается |
| :--- | :--- |
| 1. Сервер слушает сетевой адрес | Параметр `listen_addresses` |
| 2. Сетевой доступ к порту открыт | Межсетевой экран операционной системы |
| 3. Правила доступа разрешают это подключение | Файл `pg_hba.conf` |

Невыполнение любого из трёх даёт отказ, причём сообщения об ошибке в трёх случаях разные, и по ним можно понять, какое именно условие нарушено.

### Параметр listen_addresses

По умолчанию сервер слушает только локальные подключения:

```sql
SHOW listen_addresses;
```

Типичное значение после установки – `localhost`. Это значит, что подключиться можно только с той же машины.

Возможные значения:

| Значение | Что означает |
| :--- | :--- |
| `localhost` | Только локальные подключения |
| `*` | Все доступные сетевые интерфейсы |
| `10.0.31.10` | Конкретный адрес |
| `10.0.31.10, 192.168.1.5` | Перечисленные адреса |
| Пустая строка | Только через локальный сокет, без сети вовсе |

Параметр относится к классу `postmaster`, то есть **требует перезапуска сервера**:

```sql
SELECT name, setting, context FROM pg_settings WHERE name = 'listen_addresses';
```

::: warning Значение '*' и безопасность
Указание `listen_addresses = '*'` само по себе не открывает базу всему миру: подключение всё равно должно быть разрешено в `pg_hba.conf`, а роль должна пройти проверку подлинности.

Тем не менее на сервере, доступном из сети общего пользования, разумнее указать конкретные адреса интерфейсов, чтобы сервер не слушал там, где это не нужно. Задача «не принимать соединения из внешней сети» решается межсетевым экраном, а не этим параметром.
:::

### Файл pg_hba.conf

Имя файла – сокращение от **host-based authentication**, то есть «проверка подлинности на основе узла». Файл определяет, **кому, откуда, к какой базе данных и каким способом** разрешено подключаться.

Путь к файлу:

```sql
SHOW hba_file;
```

Каждая значимая строка файла имеет вид:

```
тип  база_данных  пользователь  адрес  метод  [параметры]
```

Поля разделяются пробелами или знаками табуляции.

**Поле «тип»** определяет способ соединения:

| Значение | Что означает |
| :--- | :--- |
| `local` | Локальный сокет операционной системы. Поле адреса не указывается |
| `host` | Сетевое соединение, с шифрованием или без |
| `hostssl` | Только соединение с шифрованием |
| `hostnossl` | Только соединение без шифрования |

**Поле «база данных»** принимает имя базы, список имён через запятую, либо особые значения: `all` – любая база, `replication` – подключения в режиме репликации, `sameuser` – база, одноимённая роли.

**Поле «пользователь»** принимает имя роли, список имён, `all` – любая роль, либо имя группы с префиксом `+`: `+readers` означает «любой член группы `readers`».

**Поле «адрес»** принимает адрес сети с маской в формате `10.0.31.0/24`, одиночный адрес с маской `/32`, имя узла, либо особые значения `all`, `samehost`, `samenet`.

**Поле «метод»** определяет способ проверки подлинности:

| Метод | Что делает |
| :--- | :--- |
| `trust` | Пускает без проверки. Только для локальной отладки |
| `reject` | Безусловно отказывает |
| `scram-sha-256` | Проверка пароля по современному защищённому протоколу |
| `md5` | Проверка пароля по устаревшему протоколу |
| `password` | Пароль передаётся открытым текстом. Не применять |
| `peer` | Имя пользователя операционной системы должно совпадать с именем роли. Только для `local` |
| `ident` | То же для сетевых соединений, через внешнюю службу |
| `cert` | Проверка по клиентскому сертификату |
| `ldap`, `gss`, `sspi`, `pam`, `radius` | Проверка через внешние службы |

::: danger Почему scram-sha-256, а не md5
Методичка и многие старые руководства указывают `md5`. Сегодня это следует считать устаревшим и небезопасным выбором, и причина техническая.

При методе `md5` сервер хранит и проверяет хеш, вычисленный от пароля и имени роли. Злоумышленник, добывший этот хеш из каталога `pg_authid` или перехвативший его в сети, может подключиться **не зная пароля**: хеш достаточен для прохождения проверки. Кроме того, сам алгоритм MD5 признан непригодным для защиты паролей.

Метод `scram-sha-256`, доступный с PostgreSQL 10, устраняет оба недостатка: он использует обмен вызовом и ответом, при котором перехваченные данные не позволяют подключиться повторно, и применяет стойкую функцию формирования ключа.

Переход требует двух действий. Первое – установить способ хеширования новых паролей:

```sql
SHOW password_encryption;
```

Значение должно быть `scram-sha-256`. Второе – **задать пароли заново**: существующие хранятся в формате `md5` и автоматически не преобразуются. Проверить, у кого какой формат:

```sql
SELECT rolname,
       CASE
           WHEN rolpassword LIKE 'SCRAM-SHA-256%' THEN 'scram-sha-256'
           WHEN rolpassword LIKE 'md5%'           THEN 'md5'
           WHEN rolpassword IS NULL               THEN 'пароля нет'
           ELSE 'иное'
       END AS формат_пароля
FROM pg_authid
WHERE rolcanlogin
ORDER BY rolname;
```

Только после того как у всех ролей пароли в новом формате, метод в `pg_hba.conf` можно менять на `scram-sha-256`. В обратном порядке роли потеряют возможность подключаться.
:::

### Правило первой подходящей строки

Это важнейшее правило разбора файла, и непонимание его – причина большинства ошибок настройки.

::: danger Сервер применяет первую подходящую строку и больше не смотрит
Строки файла просматриваются **сверху вниз**. Как только найдена строка, у которой совпали тип соединения, база данных, роль и адрес, применяется её метод проверки. Остальные строки **не рассматриваются**, даже если они подошли бы лучше.

Если по первой подходящей строке проверка не пройдена, подключение отвергается. Сервер **не пробует** следующие подходящие строки.

Отсюда следствие: порядок строк определяет смысл файла. Строка

```
host all all 0.0.0.0/0 reject
```

поставленная первой, запретит всё, что написано ниже. Та же строка, поставленная последней, окажется безвредной заглушкой.

Практическое правило: **частные правила выше, общие ниже.** Сначала разрешения и запреты для конкретных адресов и ролей, потом общие.
:::

### Представление pg_hba_file_rules

Проверить, как сервер прочитал файл, можно не угадывая:

```sql
SELECT line_number AS строка,
       type        AS тип,
       database    AS базы,
       user_name   AS роли,
       address     AS адрес,
       auth_method AS метод,
       error       AS ошибка
FROM pg_hba_file_rules
ORDER BY line_number;
```

Столбец `error` содержит причину, если строка не разобрана. Пустое значение означает, что строка принята.

::: tip Как проверять правки pg_hba.conf
Последовательность, избавляющая от неприятных сюрпризов:

1. Правим файл.
2. Перезагружаем конфигурацию: `SELECT pg_reload_conf();`
3. Смотрим `pg_hba_file_rules` и убеждаемся, что новая строка появилась и столбец `error` пуст.
4. Только после этого проверяем подключение.

Пропуск третьего шага – частая причина потерянного времени: опечатка в маске адреса не мешает серверу работать по старым правилам, и кажется, что перезагрузка не подействовала.

Отдельно отметим: файл `pg_hba.conf` относится к классу `sighup`. Перезапуск для его применения **не нужен**, достаточно перезагрузки конфигурации. Это ещё одна частая ошибка – перезапускать сервер там, где это излишне.
:::

### Файл pg_ident.conf

Используется только методами `ident` и `peer`, а также `gss` и `sspi`. Он задаёт соответствие между именами пользователей операционной системы и именами ролей базы данных.

Формула проста: если пользователь операционной системы называется `ivanov`, а роль в базе – `i.ivanov`, метод `peer` их не сопоставит. Файл `pg_ident.conf` позволяет описать такое соответствие:

```
# имя_карты  имя_в_системе  имя_роли
mymap        ivanov         i.ivanov
```

и указать карту в `pg_hba.conf`:

```
local all all peer map=mymap
```

### Задание 2.1. Подключение всех пользователей ко всем базам с любых адресов



В `psql`:


В pgAdmin: на панели Object Explorer в контекстном меню сервера выберите «Register – Сервер». На вкладке «General» в поле «Имя» введите произвольное название подключения, например `s1`. Нажмите «Сохранить».

В DBeaver: создайте новое подключение типа PostgreSQL и заполните те же поля.

::: tip Как отличить три причины отказа
Сообщения об ошибке подключения различаются, и по ним определяется, какое из трёх условий нарушено.

**Сервер не слушает адрес или закрыт порт:**

```
could not connect to server: Connection refused
Is the server running on host "10.0.31.10" and accepting TCP/IP connections on port 5432?
```

**Правило в `pg_hba.conf` отсутствует:**

```
FATAL:  no pg_hba.conf entry for host "10.0.31.11", user "postgres",
        database "postgres", no encryption
```

**Правило есть, но проверка подлинности не пройдена:**

```
FATAL:  password authentication failed for user "postgres"
```

Второе сообщение – самое информативное: оно перечисляет все четыре признака, по которым искалась строка. Сравнив их с файлом, причину находят сразу.
:::

::: info Формы записи адреса
Одиночный адрес записывается с маской `/32` для IPv4 и `/128` для IPv6. Подсеть – соответствующей маской: `10.0.31.0/24` охватывает адреса от `10.0.31.0` до `10.0.31.255`.

| Значение | Что охватывает |
| :--- | :--- |
| `all` | Любой адрес |
| `samehost` | Любой адрес самого сервера |
| `samenet` | Любую подсеть, к которой подключён сервер |
| `.example.com` | Любой узел домена, по обратному разрешению имён |

Применение имён узлов вместо адресов замедляет подключение, так как требует обращения к службе имён, и считается нежелательным.
:::

## Настройка клиентской стороны

### Строка подключения

Параметры подключения можно передавать по-разному, и в прикладных системах обычно применяют строку подключения:

```bash
psql "host=10.0.31.10 port=5432 dbname=postgres user=postgres sslmode=require connect_timeout=5"
```

или в виде URI:

```bash
psql "postgresql://postgres@10.0.31.10:5432/postgres?sslmode=require"
```

Полезные параметры, не имеющие отдельных ключей командной строки:

| Параметр | Назначение |
| :--- | :--- |
| `connect_timeout` | Предел времени на установление соединения |
| `sslmode` | Требования к шифрованию |
| `application_name` | Имя приложения, видимое в `pg_stat_activity` |
| `options` | Параметры сеанса, передаваемые при подключении |
| `target_session_attrs` | Требование к роли сервера: `read-write` или `any` |

::: tip Параметр application_name
Его стоит задавать всегда. Он виден в столбце `application_name` представления `pg_stat_activity`, и при разборе вопроса «чей это запрос висит два часа» избавляет от догадок.

```bash
psql "host=10.0.31.10 dbname=postgres application_name=archive_report"
```
:::

### Шифрование соединения

Параметр `sslmode` определяет требования клиента к защите соединения:

| Значение | Поведение |
| :--- | :--- |
| `disable` | Только без шифрования |
| `allow` | Предпочтительно без шифрования |
| `prefer` | Предпочтительно с шифрованием. Значение по умолчанию |
| `require` | Только с шифрованием |
| `verify-ca` | С шифрованием и проверкой удостоверяющего центра |
| `verify-full` | То же плюс проверка имени узла сервера |

::: warning Значение prefer защищает слабее, чем кажется
При значении по умолчанию клиент пытается установить защищённое соединение, но при отказе сервера **молча соглашается** на незащищённое. Это означает, что подмена сервера посередине возможна.

Для рабочих систем, работающих через недоверенную сеть, устанавливают `verify-full` и настраивают проверку сертификата. Значение `require` гарантирует только шифрование, но не подлинность сервера.

На стороне сервера шифрование включается параметром:

```sql
SHOW ssl;
```

и требует наличия файлов сертификата и ключа, пути к которым задаются параметрами `ssl_cert_file` и `ssl_key_file`.

Строки `hostssl` в `pg_hba.conf` позволяют потребовать шифрования со стороны сервера, а не оставлять решение клиенту.
:::

### Проверка текущего соединения

Изнутри сеанса полезно уметь выяснить, как именно вы подключены:

```sql
SELECT current_database()  AS база,
       current_user        AS текущая_роль,
       session_user        AS роль_подключения,
       inet_server_addr()  AS адрес_сервера,
       inet_server_port()  AS порт_сервера,
       inet_client_addr()  AS адрес_клиента,
       pg_backend_pid()    AS процесс;
```

Для локальных подключений через сокет адресные функции вернут пустые значения – это и есть признак того, что соединение локальное.

Проверить, зашифровано ли соединение:

```sql
SELECT ssl, version, cipher
FROM pg_stat_ssl
WHERE pid = pg_backend_pid();
```

13. **Проверять правки до того, как они понадобятся.** Представление `pg_hba_file_rules`, последовательность из четырёх шагов, и то, что для `pg_hba.conf` перезапуск не нужен.
14. **Настраивать клиентскую сторону.** Строка подключения в двух форматах, полезные параметры без ключей командной строки, значения `sslmode` и недостаточность значения по умолчанию, проверка собственного соединения.
15. **Различать причины отказа подключения.** Три типовых сообщения об ошибке и признак, по которому каждое опознаётся.

### Что дальше

След тетради привёл в Москву, в Разрядный архив, куда её отослали из Могилёва в 1771 году. А в 1737 году в Москве случился пожар, о котором говорил Савва Лукич в самом начале.

Правда, даты не сходятся: пожар был на тридцать четыре года раньше, чем тетрадь привезли в Москву. Значит, надежда остаётся.

В последнем учебном вопросе темы – **резервное копирование и восстановление базы данных**. И это та самая тема, которая решит судьбу поисков: вопрос не в том, где лежал оригинал, а в том, снял ли кто-нибудь с него копию.
